# Принятые решения

Короткие ADR: решение + почему + что было альтернативой.

---

## 1. Бэкенд — PocketBase

Один бинарник, SQLite, встроенные auth / файлы / realtime / админка.
Закрывает будущую авторизацию без переезда и realtime-синхронизацию сессий между
устройствами из коробки.

Альтернативы: JSON-server (нет auth, нет транзакций — упрёмся сразу),
Supabase (мощнее, но облако и лишняя сложность для внутреннего инструмента).

Интеграция с RTK Query — через кастомный `baseQuery`, оборачивающий PB SDK.
Realtime — через `onCacheEntryAdded` в нужных эндпоинтах. Не подписываемся на всё
подряд, только на активную сессию нарезки и подсчёта.

---

## 2. Android — Capacitor, не React Native

**По производительности в этом конкретном приложении разница практически нулевая.**

Что реально быстрее у RN: холодный старт (нет инициализации WebView, ~200–400мс),
нативный скролл длинных списков, жесты. Что медленнее и дороже: всё остальное для нас.

Почему Capacitor выигрывает здесь:

- Приложение — списки, формы, чекбоксы, модалки. Это ровно тот класс задач, где
  Chromium WebView на современном Android не отличим от нативного при виртуализации списков.
- Редактор геометрии куска — это SVG. В вебе он бесплатный, в RN нужен `react-native-svg`
  или Skia и переписывание всей логики указателя.
- SASS, CSS-модули, весь ui-kit переиспользуются один в один. При RN — переписывание 100% UI.
- Одна кодовая база, один тестовый набор, одна сборка.

Узкие места будут в объёме данных и количестве ре-рендеров, а не в WebView. Лечится
`@tanstack/react-virtual`, `memo` и нормальными селекторами.

RN оправдан, если появится требование к тяжёлым нативным вещам: камера с распознаванием,
Bluetooth-весы, фоновая работа. Пока таких требований нет.

---

## 3. Версионирование только у изоляции

Наборы изоляции (`insulation_sets`) версионируются по `effectiveFrom`.
Состав установки по узлам — нет. Подробности в `docs/data-model.md`.

Группы изоляции переиспользуемы между наборами: набор — это ссылки на группы, а не
их копии. Иначе правка одной группы потребовала бы обхода всех версий.

---

## 4. Чертёж — строка, а не файл

`drawingNumbers: string[]`. Файлового хранилища, вьюера и загрузки не делаем.
Поиск по номеру чертежа — по подстроке, наравне с поиском по названию.

---

## 5. Оффлайн не делаем, прогресс — на сервере

Сессии (`cutting_sessions`, `stock_sessions`) живут в БД, не в localStorage.
Работает с любого устройства, переживает закрытие вкладки, видно кто и когда считал.

Отдельной «сущности прогресса на каждый кусок» нет — один json-объект
`donePieces: Record<groupPieceId, true>` внутри записи сессии. Одна запись, один
patch, никаких сотен строк в БД на каждую нарезку.

Дебаунс записи 500мс, оптимистичное обновление в UI — отметка ставится мгновенно.

---

## 6. Площадь куска — хранится

Денормализованное производное поле `areaMm2`. Обоснование и правило единственной
точки записи — в `docs/data-model.md`.

## 7. Утверждённые зависимости

Всё остальное — только после обсуждения.

**Ядро**
`react` `react-dom` `react-router` `@reduxjs/toolkit` `react-redux` `pocketbase`

**UI-примитивы** (headless, без своих стилей, каждый 5–15кб)
`@radix-ui/react-dialog` — модалки: escape, клик вне, focus trap, портал. Модалок будет много.
`@radix-ui/react-accordion` — группы изоляции
`@radix-ui/react-checkbox` — чекбоксы карточек
`@radix-ui/react-tabs` — переключатель вида списка изоляции (по группам / по толщине)
`downshift` — поисковые дропдауны/комбобоксы (каскадные фильтры, добавление дочерних элементов)
`@floating-ui/react` — позиционирование выпадающих списков

**Данные и формы**
`react-hook-form` + `zod` — формы редактирования; `useFieldArray` ровно под блок
добавления дочерних элементов с количеством
`@tanstack/react-virtual` — виртуализация списков
`date-fns` — даты
`clsx` — классы

**Графики — библиотеку не берём.**
Нужны ровно два: кольцевой по площади групп и столбчатый по толщинам. Recharts тянет
~100кб gzip ради этого. Рисуем два компонента на голом SVG в `shared/ui/charts`.
Заодно они будут в стилистике чертежа, а не в дефолтной.

**Иконки** — `vite-plugin-svgr`, свои SVG. Готовые наборы под этот домен не подходят.

**Dev**
`vitest` `@testing-library/react` `@testing-library/user-event` `msw`
`eslint` `stylelint` `prettier` `typescript`

## 8. Структура — упрощённый FSD

`app → pages → widgets → features → entities → shared`, импорт только вниз.

Не берём каноничный FSD с жёсткими сегментами и `steiger` — для одного разработчика
это лишний обряд. Берём слои и правило направления импортов, остальное по месту.
Правило направления можно потом закрепить `eslint-plugin-boundaries`, если начнёт течь.

---

## 9. Деталь может рекурсивно состоять из деталей

`parts` получает self-relation join-коллекцию `part_parts` (`parent`, `child`,
`quantity`, `order`). В реальных данных (`docs/sample-data.md`) встречаются детали,
которые сами собираются из более мелких деталей («Фильтрующий элемент» →
«Сетка сварная» + «Лист фильтрующего материала»). Изначально `data-model.md`
считал `Part` атомарной — это было неверное упрощение, всплывшее только на
реальных данных.

Альтернатива: завести для таких случаев ещё один `Assembly`. Отклонили — это
сущность другого уровня (у сборочного узла есть номер кондиционера ввода в
эксплуатацию, свои чертежи и т.д.), а «Фильтрующий элемент» с точки зрения цеха —
рядовая деталь, просто составная. Раздувать `Assembly` под каждую составную
деталь означало бы плодить узлы там, где домен их не видит.

Циклы (`parent` не может быть потомком самого себя) PocketBase не проверяет —
валидация на уровне API-слоя при сохранении.

## 10. Правила доступа коллекций — временно полностью открыты

`listRule`/`viewRule`/`createRule`/`updateRule`/`deleteRule` всех доменных
коллекций (`units`, `assemblies`, `parts`, `insulation_*`, join-коллекции,
`*_sessions`) выставлены в `""` (публичный доступ без ограничений) в
`.pocketbase/pb_migrations/1785597925_initial_schema.js`.

Это временно: авторизации ещё нет, а фронту нужно свободно читать и писать. Когда
появится auth — сузить правила до `@request.auth.id != ''` и далее до ролей,
без переделки полей.

`users` — единственное исключение, там `createRule`/`updateRule`/`deleteRule`
оставлены дефолтными из коробки (см. `docs/data-model.md`), т.к. они и так
де-факто заперты без залогиненных пользователей.
