# CLAUDE.md

Контекст проекта для Claude Code. Читается автоматически в начале каждой сессии.

## Что это

Внутренний инструмент для производства холодильных установок: учёт состава установок
(сборочные узлы → детали), подсчёт наличия деталей на складе, отслеживание прогресса
нарезки теплоизоляции.

Пользователи — работники цеха. Основное устройство: планшет/телефон в цеху, десктоп в
конторе. **Mobile first — не декларация, а реальный основной сценарий.**

Полное ТЗ: `docs/spec.md`
Принятые решения и их обоснование: `docs/decisions.md`
Модель данных: `docs/data-model.md`
Термины RU↔EN: `docs/glossary.md`

## Стек

- React 19 + TypeScript (strict), Vite
- Redux Toolkit + RTK Query (кастомный baseQuery поверх PocketBase SDK)
- React Router v8 (data router). `RouterProvider` — из `react-router/dom`,
  всё остальное — из `react-router` (в v8 `react-router-dom` убран).
- SASS (modules) — `*.module.scss`
- PocketBase — бэкенд (БД + auth + realtime)
- Capacitor — обёртка под Android (позже, из той же кодовой базы)
- Vitest + React Testing Library + MSW

## Архитектура: упрощённый FSD

Слои сверху вниз. **Импорт разрешён только вниз по слоям.** Внутри слоя — только
через публичный `index.ts` соседнего слайса.

```
app → pages → widgets → features → entities → shared
```

- `app/` — провайдеры, store, роутинг, глобальные стили
- `pages/` — страницы, только композиция виджетов. Никакой бизнес-логики
- `widgets/` — крупные самостоятельные блоки (сайдбар, список карточек, панель статистики)
- `features/` — пользовательские сценарии (поиск, архивация, редактирование, рисование куска)
- `entities/` — доменные сущности: типы, api-слайсы, селекторы, карточка сущности
- `shared/` — переиспользуемое без доменной привязки: ui-kit, хуки, утилиты, api-клиент

Внутри слайса: `model/` (типы, слайс, селекторы), `api/`, `ui/`, `lib/`, `index.ts`.

## Правила кода

**Разделение логики и UI — жёсткое требование.**

- Компонент в `shared/ui` не знает о домене, store и api. Только props и колбэки.
- Вся логика — в кастомных хуках рядом с компонентом (`useUnitList.ts`) или в слайсе.
- Компонент-контейнер тянет данные и передаёт вниз. UI-компонент только рисует.
- Если в компоненте больше ~120 строк — декомпозируй.
- Один файл = один компонент. Именованный экспорт, не default.

**Типы**

- Никаких `any`. Если тип неизвестен — `unknown` + сужение.
- Доменные типы живут в `entities/*/model/types.ts` и реэкспортятся из `index.ts`.
- Id-типы брендированные: `type UnitId = string & { __brand: 'UnitId' }` — чтобы не
  перепутать id узла и id детали (их тут много и они однотипные).

**Состояние**

- Серверные данные — только RTK Query. Не дублируй их в слайсах.
- В слайсах — только UI-состояние: выделенные карточки, открытые модалки, фильтры.
- Прогресс нарезки и подсчёт склада — серверные сессии, а не локальный стейт.

**Оптимизация**

- `memo` на карточках списков (их сотни), `useCallback` на колбэках, уходящих в мемо-компоненты.
- Списки длиннее ~50 элементов — `@tanstack/react-virtual`.
- Селекторы через `createSelector`, никаких вычислений в `useSelector`.

## SASS

- Глобально импортируется только `_tokens.scss`, `_mixins.scss`, `_functions.scss`
  через `additionalData` в vite.config. В компонентах — `.module.scss`.
- Все цвета/отступы/радиусы — **только** через токены-переменные. Хардкод хекса = ошибка.
- Медиазапросы — только через миксин `@include respond-to(tablet)`. Mobile first,
  значит `min-width`.
- Повторяющиеся паттерны — в миксины (`@include card-surface`, `@include focus-ring`).
- Вложенность максимум 3 уровня.

## Дизайн-направление

Утилитарный интерфейс производственного инструмента, а не «дашборд-стартап».
Опорная метафора — чертёж и раскройная карта.

- Палитра холодная нейтральная (это холодильное производство): графитовые серые,
  белый лист, тонкие линии-хайрлайны. Один акцент — ледяной cyan для активного
  состояния/выделения. Янтарный — только для архива и предупреждений. Красный — только удаление.
- Цветовое кодирование типов карточек — приглушённая заливка-подложка + плотная
  цветная полоса слева. Не заливать карточку целиком.
- Цифры везде табличные (`font-variant-numeric: tabular-nums`), номера чертежей и
  установок — моноширинным. В этом приложении цифры — главный носитель смысла.
- Плотность выше средней: это рабочий инструмент, а не лендинг. Но тач-таргеты
  не меньше 44px.
- Фидбек осязаемый: мгновенная смена состояния (optimistic update), короткая
  подсветка/масштаб 150–200мс, чекбокс готовности куска должен «щёлкать» визуально.
  Никаких длинных анимаций и параллаксов.
- Обязательный пол качества: видимый focus-ring, работа с клавиатуры, `prefers-reduced-motion`.

## Домен: обязательно к пониманию

Термины и их английские соответствия — `docs/glossary.md`. **Никогда не выдумывай
свой перевод доменного термина, сверяйся с глоссарием.**

Ключевые нюансы:

1. Состав установки (узлы/детали) и набор изоляции — **независимы**. У одной установки
   может быть несколько наборов изоляции (версий); выбор версии не меняет состав установки.
2. «Чертёж» здесь — строка (номер чертежа), а не файл. По ней ищут бумажный чертёж в архиве.
3. Три разных «номера последней готовой установки» у одной установки: общий, по изоляции,
   по сборочным узлам. Это разные счётчики, не путать.
4. Площадь куска изоляции — производное поле, но хранится (денормализовано).
   Пересчёт **только** через `withComputedArea()` в `shared/lib/geometry`. Больше нигде.

## Что делать нельзя

- Не пушить в git без явной просьбы.
- Не менять схему PocketBase без обновления `docs/data-model.md` в том же коммите.
- Не добавлять зависимости без обсуждения. Список утверждённых — в `docs/decisions.md`.
- Не писать код до согласования плана, если задача крупнее одного компонента.

## Рабочий процесс

Для нетривиальной задачи: сначала план (файлы, которые тронешь, и что в них будет),
дождись подтверждения, потом код. Мелкие правки — сразу.

Коммиты атомарные, сообщения по-русски, в повелительном наклонении:
`добавь каскадные фильтры на страницу сборочных единиц`.
